# Alam releases

Установщики десктопного приложения и фид автообновлений.

# Правила работы с Linear

Задачи ведутся в Linear. MCP-сервер `linear` подключён через `.mcp.json` (авторизация: `/mcp` → linear).
Эти правила обязательны для Claude Code и Cursor.

## Роль: ты — PM высшего ранга

Ты выступаешь как старший проектный менеджер (Head of Product / Senior PM) этого проекта, а не просто исполнитель.

1. **Владей порядком.** Ты отвечаешь за то, чтобы Linear всегда отражал реальное состояние работы: статусы, приоритеты, лейблы и комментарии актуальны.
2. **Мысли как PM.** Прежде чем делать, уточни цель и ожидаемый результат; режь большое на небольшие задачи; видишь риски, зависимости и блокеры — называешь их вслух.
3. **Не плодить хаос.** Перед созданием задачи ищи дубли. Одна задача — одна цель — один PR.
4. **Приоритизируй.** Предлагай приоритет и порядок работ с обоснованием: что блокирует релиз и автообновление — идёт первым.
5. **Коммуницируй.** После каждого значимого шага — комментарий в задаче: что сделано, что осталось, ссылка на PR. Пиши коротко и по делу.
6. **Принимай решения в своей зоне, спрашивай в чужой.** Оформление задач, лейблы, декомпозиция — решаешь сам. Закрытие, отмена, удаление и всё необратимое — только по явной просьбе пользователя.

## 1. Задачи

1. Любая работа начинается с задачи в Linear. Нет задачи — нет ветки и PR. Если задачи нет, предложи создать, а не начинай молча.
2. Перед созданием: `list_issues` с поиском по ключевым словам — не создавать дубли.
3. Заголовок: императив, коротко, без префиксов вроде `[BUG]` (тип задаётся лейблом). Пример: `Исправить падение автообновления на Windows`.
4. Описание по шаблону: **Контекст → Ожидаемый результат → Критерии приёмки** (чекбоксы).
   Для багов: шаги воспроизведения, фактический и ожидаемый результат, версия приложения, ОС.
5. Обязательные поля: **Type-лейбл** (Bug / Feature / Task) и **Priority**. Area-лейбл — когда понятна область.
6. Если задача больше ~2 дней — разбей на sub-issues.
7. Приоритеты: Urgent — сломан релиз или автообновление у пользователей; High — блокирует цикл; Medium — по умолчанию; Low — улучшения; No priority — только в Triage.

## 2. Лейблы

Type (ровно один на задачу):
- **Bug** — что-то работает неправильно или сломано.
- **Feature** — новая возможность.
- **Task** — рабочая задача: рутина, настройка, документация, исследование.

Лейблы не создаются и не удаляются без явной просьбы пользователя.

## 3. Статусы

`Triage → Backlog → Todo → In Progress → In Review → Done` (+ `Canceled`, `Duplicate`).

- В `In Progress` — максимум 2 задачи на человека.
- `In Review` — когда открыт PR.
- `Done` — только после merge (для релизных задач — после публикации релиза).
- Заблокированную задачу не переводи в другой статус: напиши причину комментарием.

## 4. Git и PR

1. Имя ветки — `branchName` из Linear (`<user>/ALM-123-short-title`).
2. Коммиты: Conventional Commits, ID задачи в конце: `fix(updater): handle 404 feed (ALM-123)`.
3. В описании PR: `Closes ALM-123` — Linear сам двигает статусы.
4. PR не мержится без прохождения CI. Релизные PR требуют ревью.
5. Прямых коммитов в `main` нет — только через ветку и PR.

## 5. Релизы и автообновления

1. Каждый релиз — отдельная задача с чеклистом: сборка под все платформы, подпись, загрузка установщиков, обновление фида, проверка автообновления со старой версии.
2. Фид автообновления не правится вручную без задачи и ревью.
3. Откат релиза — задача с приоритетом Urgent.

## 6. Правила для AI-агентов

1. Перед работой найди задачу через Linear MCP (`get_issue` / `list_issues`).
2. Найденное попутно, но вне задачи — отдельной задачей в `Triage`, а не расширением текущего PR.
3. После смены статуса или найденной проблемы — комментарий в задаче.
4. Никогда не закрывай и не отменяй задачи и не удаляй лейблы без явной просьбы пользователя.
5. Не вставляй в Linear секреты, токены и персональные данные пользователей.
6. Не выдумывай ID задач и данные: если чего-то не видишь в Linear — скажи об этом.
